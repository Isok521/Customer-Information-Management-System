# 客户服务接力档案 · 第一阶段

日期：2026-09-13。目标用户：健康管理门店的管理员、前台/接待、技师。

## 1. 产品定位与范围

系统围绕客户的连续服务展开。客户档案归公司所有，服务按次留痕，员工是每次服务和跟进的参与者。核心验收问题是：一位没有接待过该客户的授权员工，能否在30秒内知道“身体情况、上次体验、当前权益、顾虑、下一步”？

不做销售漏斗、业绩排名、商机池、线索分配或复杂营销自动化。高意向只是服务沟通的上下文，不代表成交预测。身体状况与效果评价来自客户自述、门店观察，不由系统生成诊断。

本轮交付产品结构、PostgreSQL Schema、类型及数据层接口、Mock Data、可运行页面框架。演示无需 Supabase；本机存储只用于虚构演示，不能替代多人共享数据库。

## 2. 信息架构

| 一级导航 | 页面职责 | 核心操作 |
| --- | --- | --- |
| 工作台 | 今天接待谁、服务谁、跟进谁 | 打开接待档案、新建客户 |
| 客户档案 | 公司唯一客户目录 | 姓名/手机号搜索、阶段筛选、建档 |
| 服务记录 | 每次服务的独立记录 | 查看服务详情、建立本次服务 |
| 套餐 / 权益 | 客户已经购买的服务权益 | 剩余次数、有效期、使用溯源 |
| 跟进事项 | 上一次沟通之后要做什么 | 日期、顾虑、策略、负责人、来源服务 |

顶部全局搜索始终可见，结果直接进入客户详情。桌面固定侧栏，平板缩为图标导航，数据表可横向滚动。

## 3. 页面结构与路由

| 页面 | 路由 | 第一版内容 |
| --- | --- | --- |
| 工作台 | `/` | 5项指标、今日预约/服务、待跟进、最近更新 |
| 客户列表 | `/customers` | 搜索、筛选、症状、阶段、最近服务、剩余权益 |
| 新建客户 | `/customers/new` | 基础接待信息与初步健康诉求，可本地保存 |
| 客户详情 | `/customers/[id]` | 接待摘要卡 + 5个 Tabs |
| 新建服务 | `/customers/[id]/services/new` | 从档案进入，默认该客户 |
| 服务入口 | `/services/new` | 从工作台进入，先选择客户 |
| 服务列表 | `/services` | 搜索、服务状态筛选、日期倒序 |
| 服务详情 | `/services/[id]` | 服务前、即时记录、结束结果、独立续单区 |
| 权益总览 | `/packages` | 余额卡、状态筛选、每笔使用对应服务 |
| 跟进事项 | `/follow-ups` | 待跟进/已跟进筛选、沟通背景入口 |

客户详情顶部：姓名、性别/年龄、手机号、当前阶段、标签；三列依次呈现身体问题与核心需求、最近已完成服务与反馈、权益与顾虑；底部一条突出下一步和责任人。当前未完成服务单独提供入口，不覆盖最近一次完成结果。

下方 Tabs：

- 概览：服务/购卡/首次到店时间线，旁侧健康注意事项、权益和最近沟通。
- 健康档案：基础健康信息、测量来源、诉求、偏好、消费观念、禁忌、接待信息。
- 服务记录：所有服务，包含预约、进行中和已完成；每条打开完整服务。
- 套餐/权益：按客户已购权益展示余额和历史扣次。
- 跟进记录：保留推荐内容、原话、反应、顾虑、策略、责任人及来源服务。

## 4. 核心流程与阶段

新客：搜索确认未建档 → 快速建档 → 补全健康问卷 → 可选购卡 → 服务前确认 → 服务中即时记录 → 结束结果 → 可选续单沟通 → 下一步计划。

老客：搜索姓名/手机号 → 30秒摘要 → 必要时查看历史 → 确认当前状态与权益 → 新建本次服务。

服务状态：`scheduled → in_progress → completed`；未完成服务可取消。已完成记录不直接覆盖；未来通过有审计的更正流程处理。第一版允许直接建立 in_progress；预约改期、签到与取消按钮属于后续工作。

套餐状态：存储 active / frozen / cancelled；expired 和 exhausted 由日期与余额计算。开始服务不扣次，完成服务时才写使用流水。使用1次对应1条已完成服务；同次服务不得重复扣次。

续单沟通：必须先选择是否进行，选择“否”不阻止服务完成；选择“是”后补充推荐、反应、顾虑、原话和下一步。后续完成接口应在同一事务里保存服务结果、权益使用、跟进计划。独立回访允许 session_id 为空，但必须归属于客户。

## 5. 首页统计口径

| 指标 | 口径 |
| --- | --- |
| 客户总数 | 当前客户档案数；真实模式应排除归档客户 |
| 今日新增 | 首次到店日期为门店当天 |
| 今日服务人数 | 当天 in_progress / completed 的去重客户，不含预约与取消 |
| 待跟进客户 | 存在 pending 事项的去重客户；逾期不自动消失 |
| 高意向客户 | 当前含“高意向”标签的客户，不累计历史意向 |

演示日期固定2026-09-13，防止样例过几天就全部变成历史。接入真实数据库后统一用 Asia/Shanghai 计算当天，不能沿用固定日期。

## 6. 业务假设

- 第一版面向一个公司的一家门店。暂不实现多租户；扩展 SaaS 前需引入 organization_id、门店归属及跨租户 RLS。
- 大陆11位手机号暂作唯一查重键。姓名不唯一；同名可并存。家庭共用手机与无手机号客户需先确认规则，再调整唯一约束，不用虚构手机号绕过。
- 每客户最多一条进行中服务，可有多条预约；前台搜索遇到服务中记录时优先继续该记录。
- 客户档案不绑定“唯一所有员工”。接待人、服务人、记录人、跟进负责人各有独立字段。
- package 表代表客户已购权益；不混同推荐方案或未来套餐商品目录。
- 退款、赠送、补扣、撤销、延期需单独的审计账本，当前不直接修改已使用次数。

## 7. 本轮验收

| 模块 | 门店业务检查 | 当前边界 |
| --- | --- | --- |
| 客户列表 | 姓名和手机号都能找人；无结果明确提示；手机号重复不建档 | 快速建档可保存，完整问卷编辑后续补齐 |
| 接待摘要 | 陈玉兰可见症状、第二次反馈、剩1次、价格/医保顾虑、下一步 | 显示人工记录，不加入AI推断 |
| 服务框架 | 有进行中记录时不能重复创建；可不使用套餐 | 支持服务建立；结束与即时记录写入尚未开放 |
| 套餐权益 | 3次体验卡仅有2次完成扣次；09-13进行中仍剩1次 | 查看和结构完成，购买/退款尚未实现 |
| 客户时间线 | 可追溯两位技师的服务和每次对应沟通 | 第一版聚合服务、购卡、建档；独立回访在跟进Tab查看 |
| 数据安全 | Schema 默认拒绝匿名读取；员工role由可信记录管理 | 未接入登录，不能用于真实健康数据运营 |

## 8. 下一阶段建议顺序

1. 健康问卷完整编辑与客户标签维护。
2. 即时记录保存、服务结束表单、续单条件表单、跟进计划。
3. Supabase Auth、员工可信身份、最小角色授权、事务RPC与审计。
4. 套餐购买和完成时扣次、幂等、防余额超扣、并发验证。
5. 预约签到、实际回访记录、聚合完整时间线及接力场景验收。

每步独立验证后继续，不把服务完成、权益消费和跟进保存拆成易产生半成功的多次浏览器写入。
